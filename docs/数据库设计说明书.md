# 数据库设计说明书

## 1. 文档说明

本系统当前未使用 MySQL、PostgreSQL、SQLite 等传统关系型数据库。系统数据采用“JSON 文件 + 文件系统目录”的轻量持久化方案。因此本文档中的“数据库设计”指系统持久化数据结构、文件表设计、目录结构、字段说明、索引元数据和备份恢复方案。

## 2. 数据存储总览

| 数据类别 | 存储位置 | 存储方式 |
| --- | --- | --- |
| 用户、员工、权限 | `photo-backend/users.json` | JSON 数组 |
| 部门 | `photo-backend/departments.json` | JSON 数组 |
| 监控照片 | `photo-backend/photos/` | 文件目录 |
| 照片缩略图 | `photo-backend/.thumbnails/` | 文件目录，可再生成 |
| 办公资料文件 | `photo-backend/office_data/` | 文件目录 |
| 办公资料元数据 | `photo-backend/office_data/.metadata.json` | JSON 对象 |
| 短信发送日志 | `photo-backend/office_data/sms_logs.json` | JSON 数组 |
| 上传客户端配置 | 本机 `%LOCALAPPDATA%/PhotoMonitorUploader/config.json` | JSON 对象 |
| 上传客户端状态 | 本机 `%LOCALAPPDATA%/PhotoMonitorUploader/uploaded_state.json` | JSON 对象 |

Docker 部署时，以下目录或文件通过 volume 持久化：

```yaml
volumes:
  - ./photo-backend/photos:/app/photos
  - ./photo-backend/office_data:/app/office_data
  - ./photo-backend/users.json:/app/users.json
```

## 3. 用户员工表设计

### 3.1 存储文件

```text
photo-backend/users.json
```

### 3.2 数据结构

根节点为用户数组，每个元素表示一个管理员或员工账号。

```json
[
  {
    "username": "admin",
    "password": "pbkdf2_sha256$260000$...",
    "role": "admin",
    "phone": "",
    "name": "系统管理员",
    "age": 0,
    "department": "",
    "position": "",
    "rank": "",
    "id_number": "",
    "birthday": "",
    "home_address": "",
    "emergency_contact": "",
    "certificates": [],
    "avatar": "👨‍💼",
    "join_date": "2026-07-08 09:00:00",
    "permissions": []
  }
]
```

### 3.3 字段说明

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| username | string | 是 | 登录用户名，系统内唯一 |
| password | string | 是 | 密码，支持旧明文自动迁移到 PBKDF2-SHA256 |
| role | string | 是 | `admin` 或 `employee` |
| phone | string | 否 | 手机号，也是创建员工时默认用户名和密码来源 |
| name | string | 否 | 姓名，未填时前端显示 username |
| age | number | 否 | 年龄，当前保留字段 |
| department | string | 否 | 所属部门 |
| position | string | 否 | 岗位 |
| rank | string | 否 | 职级 |
| id_number | string | 否 | 身份证号，可用于解析生日 |
| birthday | string | 否 | 生日，格式 `YYYY-MM-DD` |
| home_address | string | 否 | 家庭住址 |
| emergency_contact | string | 否 | 紧急联系人 |
| certificates | array | 否 | 证书信息列表 |
| avatar | string | 否 | 头像显示字符 |
| join_date | string | 否 | 加入时间 |
| permissions | array | 否 | 权限矩阵字符串列表 |

### 3.4 证书子结构

```json
{
  "name": "安全员证",
  "number": "CERT-001",
  "expires_at": "2026-12-31",
  "note": "复审提醒"
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| name | string | 证书名称 |
| number | string | 证书编号 |
| expires_at | string | 到期日期，格式 `YYYY-MM-DD` |
| note | string | 备注 |

### 3.5 权限字段设计

权限格式：

```text
perm:<system>:<department>:<action>
```

支持的 system：

| system | 说明 |
| --- | --- |
| photos | 监控照片 |
| company_files | 公司文件 |
| study_articles | 学习交流 |
| ledgers | 台账管理 |
| structure | 公司架构 |

支持的 action：

| action | 说明 |
| --- | --- |
| read | 查看 |
| create | 新增或上传 |
| update | 修改 |
| delete | 删除 |

示例：

```text
perm:photos:运营部:read
perm:photos:运营部:create
perm:company_files:*:read
perm:ledgers:财务部:create
perm:structure:*:read
```

特殊规则：

- `department` 为 `*` 表示全部部门。
- `role=admin` 时忽略 `permissions`，视为拥有全部权限。
- `structure` 当前只支持 `read` 动作。

## 4. 部门表设计

### 4.1 存储文件

```text
photo-backend/departments.json
```

### 4.2 数据结构

根节点为字符串数组：

```json
[
  "运营部",
  "财务部",
  "工程部"
]
```

### 4.3 设计规则

- 部门名称保存前会 trim。
- 部门名称不能为空。
- 部门列表会去重并按名称排序。
- 部门改名时，同步更新员工所属部门和权限矩阵中的部门字段。
- 删除部门前会检查是否存在员工或上传资料引用。

## 5. 监控照片存储设计

### 5.1 存储目录

```text
photo-backend/photos/
```

### 5.2 目录结构

```text
photos/
  <部门>/
    <站点>/
      <日期区间>/
        <图片文件>
```

示例：

```text
photos/
  运营部/
    xiazhan/
      2026_07_08-2026_07_08/
        IMG_20260708103000_001.jpg
```

### 5.3 支持格式

照片读取支持：

- `.jpg`
- `.jpeg`
- `.png`
- `.webp`

照片上传接口还允许部分压缩包和数据文件扩展名，具体由后端 `ALLOWED_UPLOAD_EXTS` 控制。

### 5.4 照片元数据生成

照片列表接口不使用单独表，而是实时扫描目录并生成以下元数据：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| name | string | 文件名 |
| url | string | 原图接口地址 |
| thumbnail_url | string | 缩略图接口地址 |
| time | number | 用于排序和过滤的时间戳 |
| actual_time | number | 实际拍摄或文件时间戳 |
| actual_time_text | string | 展示时间 |
| filesystem_time | number | 文件系统修改时间 |
| size | number | 文件大小 |
| folder | string | 文件所在目录 |
| department | string | 部门 |

### 5.5 缩略图缓存

缩略图目录：

```text
photo-backend/.thumbnails/
```

生成规则：

- 请求 `/thumbnails/{file_path}` 时按需生成。
- 最大尺寸为 `360 x 360`。
- 缩略图格式为 JPEG。
- 原图更新后，缩略图会重新生成。
- 缩略图可删除后自动重建，不作为核心数据备份对象。

## 6. 办公资料存储设计

### 6.1 存储目录

```text
photo-backend/office_data/
```

### 6.2 目录结构

```text
office_data/
  company_files/
    <部门>/
      <YYYY_MM_DD>/
        <文件>
  study_articles/
    <部门>/
      <YYYY_MM_DD>/
        <文件>
  ledgers/
    <部门>/
      <YYYY_MM_DD>/
        <文件>
  .metadata.json
  sms_logs.json
```

### 6.3 元数据文件

```text
photo-backend/office_data/.metadata.json
```

根节点为对象，key 为 upload_id，value 为文件元数据。

```json
{
  "6d2a2a7e7e6c4df28f9f7d0b0d9b3b22": {
    "id": "6d2a2a7e7e6c4df28f9f7d0b0d9b3b22",
    "name": "安全检查表.xlsx",
    "category": "ledgers",
    "department": "运营部",
    "size": 102400,
    "sha256": "abcdef...",
    "path": "ledgers/运营部/2026_07_08/安全检查表.xlsx",
    "content_type": "application/vnd.openxmlformats-officedocument.spreadsheetml.sheet",
    "uploaded_by": "zhangsan",
    "uploaded_at": "2026-07-08 09:30:00",
    "time": 1783483800.0
  }
}
```

### 6.4 元数据字段说明

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | string | 上传 ID，UUID hex |
| name | string | 保存后的文件名 |
| category | string | 分类：`company_files`、`study_articles`、`ledgers` |
| department | string | 归属部门 |
| size | number | 文件大小，字节 |
| sha256 | string | 文件 SHA-256 摘要 |
| path | string | 相对 `office_data` 的路径 |
| content_type | string | MIME 类型 |
| uploaded_by | string | 上传人用户名 |
| uploaded_at | string | 上传时间 |
| time | number | 上传时间戳 |

### 6.5 分类扩展名约束

| 分类 | 允许扩展名 |
| --- | --- |
| company_files | 图片、zip、csv、xlsx、xls、json、txt、pdf |
| study_articles | pdf、doc、docx、ppt、pptx、txt、md、html、htm、zip |
| ledgers | csv、xlsx、xls、json、txt、pdf、zip |

## 7. 短信日志表设计

### 7.1 存储文件

```text
photo-backend/office_data/sms_logs.json
```

### 7.2 数据结构

根节点为日志数组：

```json
[
  {
    "key": "birthday:2026-07-08:zhangsan",
    "type": "birthday",
    "username": "zhangsan",
    "phone": "13800000000",
    "template_code": "SMS_506865121",
    "template_params": {
      "name": "张三"
    },
    "sent_at": "2026-07-08 09:00:00",
    "dry_run": true,
    "status": "success",
    "provider_response": {
      "dry_run": true
    }
  }
]
```

### 7.3 字段说明

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| key | string | 去重键，同一天同一事件只成功发送一次 |
| type | string | `birthday` 或 `certificate` |
| username | string | 员工用户名 |
| phone | string | 接收手机号 |
| template_code | string | 阿里云短信模板 code |
| template_params | object | 模板参数 |
| sent_at | string | 执行时间 |
| dry_run | boolean | 是否干跑 |
| status | string | `success` 或 `failed` |
| provider_response | object | 阿里云返回或干跑结果 |
| error | string | 失败原因 |

## 8. 上传客户端本地数据设计

### 8.1 配置文件

默认路径：

```text
%LOCALAPPDATA%/PhotoMonitorUploader/config.json
```

主要字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| server | string | 服务端地址 |
| token | string | 登录 token |
| username | string | 用户名 |
| department | string | 上传部门 |
| station | string | 默认站点 |
| watch_dir | string | 本地监听目录 |
| interval_seconds | number | 轮询间隔 |
| stable_seconds | number | 文件稳定等待时间 |
| timeout_seconds | number | 请求超时时间 |
| retry_count | number | 上传重试次数 |
| retry_delay_seconds | number | 重试间隔 |
| include_subdirectories | boolean | 是否包含子目录 |

### 8.2 已上传状态文件

默认路径：

```text

```

key 由文件绝对路径、文件大小、文件修改时间组成，value 记录上传时间、站点和服务端返回项。

## 9. 数据一致性设计

### 9.1 JSON 写入一致性

- `users.json` 和 `departments.json` 保存时直接写入目标文件。
- `office_data/.metadata.json` 保存时先写临时文件，再替换目标文件。
- 上传文件先写临时文件，再替换为正式文件。

### 9.2 部门一致性

部门改名时：

1. 更新 `departments.json`。
2. 更新员工 `department` 字段。
3. 更新员工 `permissions` 中引用旧部门的权限矩阵。
4. 迁移 `photos/<部门>` 和 `.thumbnails/<部门>` 下的历史文件。
5. 迁移公司文件、学习交流和台账目录，并同步更新 `.metadata.json` 中的 `department` 与 `path`。

部门删除时：

1. 检查员工、权限、监控照片、缩略图、办公资料和上传元数据。
2. 全部无引用时允许直接删除。
3. 存在引用时必须选择另一个现有部门，先迁移全部关联数据，再删除原部门。

迁移前会检查目标路径冲突，不会覆盖已有文件。迁移过程中会保存 JSON 快照并记录已移动文件；任一步失败时反向移动文件并恢复 `departments.json`、`users.json` 和 `.metadata.json`。

部门列表同时汇总部门配置、员工与权限、照片目录、三类办公资料目录和上传元数据。旧名称即使已经不在 `departments.json` 中，只要仍有历史数据就会在部门管理中显示，管理员可将其迁移到现有部门后清除。

### 9.3 文件与元数据一致性

办公资料列表接口以 `.metadata.json` 为主，同时会扫描目录补充没有元数据的遗留文件。下载、预览、删除必须通过 upload_id 查找元数据，并确认文件实际存在。

## 10. 备份与恢复设计

### 10.1 必备备份对象

建议定期备份：

```text
photo-backend/users.json
photo-backend/departments.json
photo-backend/photos/
photo-backend/office_data/
.env
certs/
```

### 10.2 可选备份对象

```text
photo-backend/.thumbnails/
```

缩略图可由原图重新生成，因此不是必须备份对象。

### 10.3 备份命令示例

```bash
tar -czf photo-monitor-backup-$(date +%F).tar.gz \
  .env \
  certs \
  photo-backend/users.json \
  photo-backend/departments.json \
  photo-backend/photos \
  photo-backend/office_data
```

### 10.4 恢复步骤

1. 停止容器：

```bash
docker compose down
```

2. 解压备份到项目目录。
3. 确认 `users.json`、`photos`、`office_data` 权限可读写。
4. 启动容器：

```bash
docker compose up -d --build
```

5. 登录系统检查用户、照片和办公资料是否恢复。

## 11. 迁移建议

当出现以下情况时，建议迁移到关系型数据库：

- 员工和权限数据需要复杂查询和审计。
- 多管理员并发编辑频繁。
- 上传资料量较大，需要分页、检索、统计和生命周期管理。
- 需要操作日志、审批流、数据报表。

推荐迁移方向：

- PostgreSQL 或 MySQL 存储用户、部门、权限、上传元数据、短信日志。
- 对象存储或 NAS 存储照片和文件。
- Redis 用于在线会话、WebSocket 广播和异步任务队列。
